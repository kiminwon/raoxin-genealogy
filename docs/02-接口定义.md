# 饶信谱脉 · 家谱小程序接口定义

> 版本 V1.0 ｜ 2026-09-24 ｜ 配套 `schema.sql`、`家谱小程序-数据库设计.md`、`家谱小程序-页面流程.md`

## 0. 通用约定

### 0.1 基础

| 项 | 约定 |
|---|---|
| Base URL | `https://api.<域名>/v1` |
| 协议 | HTTPS，JSON（`Content-Type: application/json`） |
| 鉴权 | `Authorization: Bearer <token>`，token 由 `/auth/login` 换取，有效期 7 天 |
| 时间格式 | ISO 8601 字符串 `2026-09-24T14:30:00+08:00` |
| 日期格式 | `YYYY-MM-DD`，精度不足时补 `01-01`，另用 `precision` 字段标明真实精度 |
| 坐标系 | 单位 **px**，基于 750 宽设计稿；小程序端按 `rpx = px * (屏宽 / 375)` 换算 |

### 0.2 统一响应包装

```json
{ "code": 0, "msg": "ok", "data": { } }
```

失败时：

```json
{ "code": 40301, "msg": "您没有编辑该节点的权限", "data": null }
```

### 0.3 错误码

| code | 含义 | 客户端处理 |
|---|---|---|
| 0 | 成功 | — |
| 40001 | 参数错误 | 提示具体字段 |
| 40100 | 未登录 / token 失效 | 静默重新登录后重试一次 |
| 40300 | 无权限访问该资源 | 提示并引导申请 |
| 40301 | 无编辑权限（不在 `edit_scope` 内） | 弹窗引导"申请扩展授权" |
| 40302 | 邀请码无效 / 已过期 / 已耗尽 | 提示"链接已失效，请联系邀请人" |
| 40401 | 资源不存在 | 提示并返回上一页 |
| 40901 | 认领冲突（该节点已被他人认领） | 展示冲突说明，引导联系房长 |
| 40902 | 编辑冲突（同一字段存在其他待审修订） | 提示"已有他人提交该字段的修改" |
| 42900 | 频率限制 | 退避重试 |
| 50000 | 服务端错误 | 通用错误提示 |

### 0.4 脱敏约定（决策第 4 条）

**所有返回人物的接口，字段值均已按访问者身份脱敏完毕，客户端不做任何脱敏逻辑。**

这是刻意的分工：脱敏规则放在客户端意味着反编译小程序的成本极低，而且改规则要发版。放在服务端，客户端拿到的就是它有权看到的最终结果。

脱敏后的姓名形如 `陈*明`。当用户**认领成功**（答题自证通过）后，同一接口返回全族在世者的**全名**——不需要切换接口，只是返回内容不同。

分界线是"有没有认领"，不是"是不是近亲"（2026-10-16 调整）。原来只给近亲全名，结果是认领之后打开全族总览，伯父、堂侄那一支全是 `陈*梁`、`陈*华`，而这一屏存在的意义就是看清整个族。

**但只放开姓名**：生日精度、职业、生平仍只对近亲（直系上下 3 代 + 兄弟姐妹 + 配偶）开放。未认领的访客一律照旧脱敏——族浏览码会被转发到族外，那一档不能松。

服务端在响应头返回当前视角标识，便于客户端调试：

```
X-Viewer-Scope: guest | lineage | close | admin
```

## 1. 认证 auth

### POST `/auth/login`

微信 `wx.login()` 换取的 code 登录。

**请求**
```json
{ "code": "0a1b2c3d...", "inviteCode": "AB12CD34" }
```
`inviteCode` 可选，用于记录"这个用户是从谁的邀请进来的"。

**响应**
```json
{
  "token": "eyJhbGciOi...",
  "expiresIn": 604800,
  "user": {
    "id": 1001,
    "role": 1,
    "familyId": 5,
    "claimedPersonId": 10086,
    "needClaim": false
  },
  "pendingInvite": {
    "codeType": 2,
    "familyId": 5,
    "anchorPersonId": 10020,
    "anchorName": "陈*海",
    "scopeNodeCount": 11
  }
}
```

`pendingInvite` 在带邀请码进来且尚未接受时返回，客户端据此弹"你要加入陈国栋这一支的填写吗？"的确认框。

### GET `/auth/me`

返回当前用户状态，用于小程序启动时判断走哪个首屏。

### GET `/auth/identify/quiz` —— 答题自证：出题

身份确认的第一步。**这是现在的主通道**：房长年纪大、不会操作审批界面，
而同一族的码只会分享给族人，冒领罕见；阻塞的代价远大于冒领的代价。

需登录。**未入族时返回 `40001`**（`msg` 里会提"族浏览码/邀请码"）——
客户端遇到这个码应当把用户送到**家族码输入页**，而不是把这句话弹给用户。

入族的唯一路径是 `POST /invite/{code}/accept`；`?familyId=` 只在开发期
（直接指定某个族调试）使用，**不要**拿它当生产的入族手段：
家谱里已故先人的全名在树上对外是公开的，一个能随手拼进链接的 query 不能当门票。

```jsonc
{"code":0,"msg":"ok","data":{
  "familyId": 1, "familyName": "广信陈氏",
  "personCount": 19, "generationCount": 5, "livingCount": 11,
  "questions": [
    {"key":"relation","type":"choice","required":true,"label":"您和家谱里的哪一位最亲？",
     "defaultValue":"father",
     "options":[{"value":"father","label":"我父亲"},{"value":"mother","label":"我母亲"},
                {"value":"spouse","label":"我配偶"}],
     "hint":"嫁入本族的媳妇、入赘的女婿，请选「我配偶」"},
    {"key":"relativeName","type":"text","required":true,"label":"他/她的名字","strength":"strong",
     "hint":"按家谱上的写法填，繁体、简体都可以"},
    {"key":"selfName","type":"text","required":true,"label":"您自己的名字"},
    {"key":"extraName","type":"text","required":false,"label":"另一位家长的名字（选填）",
     "hint":"同名较多时，多填一位能帮我们确认是哪一支"}
  ],
  "alreadyClaimed": null,   // 已认领则回 {personId, name, generation}
  "hint": "答对就能直接进入，不需要等谁批。"
}}
```

`personCount` 不是装饰：用户据此判断"是不是我们这个族"。

### POST `/auth/identify/verify` —— 答题并自动确认身份

```jsonc
{"relation":"father",        // father / mother / spouse
 "relativeName":"陈国栋",     // 所填亲属的姓名（繁简、含间隔号都可）
 "selfName":"陈启华",         // 本人的姓名
 "extraName":"李秀英",        // 选填：另一位家长
 "selfGender":1,             // 选填：1男 2女，用来定新节点的性别
 "inviteCode":"CHEN2026"}    // 选填：仅留痕
```

四种结果，**四种都是正常业务分支，不是异常**：

| `data.result` | 含义 | `data` 里还有什么 |
|---|---|---|
| `matched` | 谱上有你，唯一命中 | `personId` `generationLabel` `grantedNodeCount` `filledFields` `evidenceStrength` |
| `new_member` | 谱上有你父亲、**谱上还没你**（主路径） | `personId` `relativeId` `generationLabel` `grantedNodeCount` `evidenceStrength` |
| `ambiguous` | 同名多个，或证据不足 | `candidates`（同名时给脱敏简介）或 `needExtra:true` + `reason` |
| `no_match` | 对不上，或所填是已故先祖 | `fallback.channel="manual_claim"` + `hint` |

错误码：`40901` 该节点已被他人认领（转人工，不做先到先得）；
`42900` 限速（10 次/小时，连续真答错 5 次冷却；响应带 `retryAfterSeconds`，系统态错误不计入失败，理事会可解禁）；`40001` 未入族。

**证据强度**由所填亲属是否在世决定，会写进 `claim.verify_answers` 留痕：

| 所填亲属 | 树上显示 | `evidenceStrength` |
|---|---|---|
| 在世 | `陈*栋` | `strong` —— 外人抄不到 |
| 已故 | `陈国栋` | `weak` —— 名字就在屏幕上 |

`weak` 且要**新建节点**时会追一道门槛：返回 `ambiguous` + `needExtra:true`，
要求再答一位家长的名字。`matched` 路径不受影响。

> **`matched` 顺手补空位**：若另一位家长在谱上只记着「配某氏」（`name IS NULL`），
> 就用 `extraName` 把名字补上——只填空、绝不覆盖已有原文。
> 结果在 `data.filledFields`：`[{personId, relation, before:"王氏", after:"王丽", revisionId}]`。
> 补写同样留 `AUTO_MERGED` 修订，可回滚。

**认领成功后**：`app_user.claimed_person_id` 绑定；`edit_scope` 写入
「自己 + 直系上下两代」（`close_relatives(up=2, down=2)`）；写 `claim`
（`verify_method=1` 答题自证、`status=2` 直接通过）、`notification`、`audit_log`。

### 写操作的两种去向

所有写接口（`PATCH /person/{id}`、`POST /person`、`POST /person/{id}/missing/submit`）
的响应都带 `data.autoMerged`（bool），端上据此说"已生效"还是"等房长确认"：

| 用户状态 | 目标在 `edit_scope` 内？ | `autoMerged` | `status` |
|---|---|---|---|
| 房长及以上 | — | `true` | 4（AUTO_MERGED） |
| 已认领 | 是 | `true` | 4 |
| 已认领 | 否 | `false` | 1（待审，**不 403**） |
| 未认领 | — | — | 40301 |

> `autoMerged` **必须显式返回**，不能只塞在 `nextHint` 文案里：
> 端上拿到 `undefined` 会一律显示"排队中"，把已生效的写入误报成待审，
> 用户以为没保存就会重复提交。

## 2. 邀请码 invite（决策第 5 条，2026-10-22 修订）

> **编辑码（`codeType=2`）已下线。** 现在只有一种码：族级浏览码。
>
> 原因三条：① 权限不该由链接携带——写权限本来就绑在 `viewer.can_edit(pid)`（`edit_scope`），而它唯一正常的来源是**认领**；编辑码等于在身份系统之外开一条查不到人的写权限后路。② 代录需求不需要它——理事会成员（`role=2`）本来就全族可写，志愿者分房录入走角色 + `POST /admin/grant-scope`（可追溯、可撤销）。③ 实测它一次都没被用过：本地与云端 `used_count` 全为 0，`edit_scope` 里 `source=2` 的授权行一条都没有。
>
> **个人分享仍然保留，但它带的是「锚点」不是「权限」。** 分享路径形如
> `/pages/landing/landing?code=CHEN2026&anchor=10086`，被分享人**点开就直接进族**（不用手输家族码），
> 并且未认领时「我的一家」先聚焦到分享人身上——他第一眼看到的是自己认得出的名字。
> 能改什么，仍然只由他自己认领后的 `edit_scope` 决定。

### GET `/invite/{code}` —— 落地页预览

**无需登录。** 这是分享链路的第一步，绝不能挡在登录后面。

**一个接口担两个角色**：它既是"点链接进来"的预览，也是**输码页的查码接口**——
用户在家族码输入框里敲完码，端上就是拿它去查"这个码对不对、是哪个族"。
所以它必须给出足够让人确认"是这家"的信息（堂号、始迁祖、人数、三代脱敏预览）；
查不到时回 `40302`，端上据此退回输码态并允许当场换一个码，而不是把页面堵死。

**参数**

| 名 | 必填 | 说明 |
|---|---|---|
| `previewPersonId` | 否 | 想预览哪个人的附近三代。**分享链接传的就是分享人**，所以落地页一打开就是"分享人这一家"的上下三代 |

**响应**
```json
{
  "valid": true,
  "codeType": 1,
  "family": {
    "id": 5,
    "name": "广信陈氏",
    "surname": "陈",
    "tangHao": "颍川堂",
    "settlePlace": "上饶市广信区茶亭镇",
    "personCount": 2864,
    "generationCount": 24
  },
  "inviter": { "nickname": "国栋", "personId": 10086 },
  "anchor": {
    "id": 10020,
    "personId": 10020,
    "displayName": "陈*海",
    "gender": 1,
    "generation": 19,
    "generationLabel": "第十九世",
    "livingStatus": 1
  },
  "scopePreview": null,
  "preview": {
    "generations": [
      {
        "generation": 18,
        "label": "第十八世",
        "persons": [
          { "id": 10012, "displayName": "陈*栋", "gender": 1, "birthYear": 1965, "livingStatus": 1, "isAnchorPath": true }
        ]
      }
    ],
    "note": "仅展示三代脱敏信息，加入后可查看完整世系"
  }
}
```

`anchor` 取 `previewPersonId`；没传时退回码本身的历史锚点（编辑码才有）。**锚点无效（不属于该族）时静默降级为"从始祖往下三代"**，不报错——分享出去的人可能早被合并了，不能因此让整页打不开。

**为什么落地页只给三代：** 一来是隐私边界（未登录用户不该看到全族在世者的数据），二来是转化设计——**"这是你家，但只给你看三代"比"这里什么都没有"更能促使人认领。** 缺口本身就是动机。

### POST `/invite/{code}/accept`

**需登录。** 接受邀请：消耗次数、把当前族切到该族、建立 `user_family` 行。

| 参数 | 位置 | 说明 |
|---|---|---|
| `anchorPersonId` | query | 分享链接里的锚点（分享人）。服务端校验它属于本族后原样回传，端上据它决定「我的一家」先看谁 |

**响应**
```json
{
  "codeType": 1,
  "familyId": 5,
  "role": 1,
  "claimedPersonId": null,
  "needClaim": true,
  "grantedScopes": { "personIds": [], "nodeCount": 0 },
  "recommendAnchor": 10086
}
```

`recommendAnchor` **不是**"你可能是我"的判定（认领仍然靠答题自证），它只回答"进来先看谁"：优先取请求里的 `anchorPersonId`，其次历史编辑码签发时的锚点，都没有则 `null`。

**为什么锚点要经服务端回传、而不让端上只信 URL**：链接里的 `anchor` 可能指到别的族的人（用户后来切过族）。端上直接拿去请求 `/tree` 会拿到 `40001`，整页空白。服务端校验一次，端上就有一个可信的值。

### GET `/invite/mine`

我生成过的码列表（含历史编辑码）。**端点保留是为了让老的码能查用量、能吊销**，端上已不再展示这一块。

### POST `/invite/generate`

**只签发族级浏览码（`codeType=1`）。** 族管理员及以上调用；已存在的码直接复用（幂等）。

```json
{ "familyId": 5, "codeType": 1 }
```

```json
{
  "code": "CHEN2026",
  "codeType": 1,
  "scopeNodeCount": null,
  "shareText": "广信陈氏的电子家谱 · 点开直接进，看看您在族里的位置"
}
```

**`codeType=2` 一律回 `40001`**，`msg` 是"个人编辑码已下线：分享家族链接即可，家人认领自己之后就能填自己那一支"。

⚠️ 这里必须**明确报错、不能静默降级成浏览码**：线上旧版端拿返回值里的 `scopeNodeCount` 会显示"已授权 11 个节点"，那是在骗用户。报错才能让旧端走进 catch 并换提示。

### 浏览码是懒生成的（`GET /family/mine`）

**任何族成员**读 `/family/mine` 时，如果族里还没有浏览码，服务端就补一个（`view_code_enabled=1` 的前提下）。

理由是分享本身就是接力修谱的起点：只有管理员能生成码的话，普通族人点分享只会得到一个**不带码**的链接，对方还是得手输家族码——那正是"分享出去却进不来"的那道坎。

权限边界没有松动：浏览码给的是**看脱敏全族树**，而能调这个接口的人本来就是本族成员、本来就能看到这棵树。族里要关掉对外分享，把 `view_code_enabled` 置 0，此后既不补码、`viewCode` 也返回 `null`，端上隐藏分享按钮。

### 分享链接的三种形态

| 形态 | 带不带得动分享人 | 现状 |
|---|---|---|
| 微信聊天里的**分享卡片**（`onShareAppMessage`） | 能，`path` 里任意 query | ✅ 已实现：`?code=<族码>&anchor=<分享人>` |
| **小程序码**（`wxacode.getUnlimited`，可打印贴祠堂） | 能，但 `scene` 上限 32 字符，用短格式 `CHEN2026-10086` | 端上已能解析，**生成图片的接口未做** |
| 普通**链接二维码** / URL Link | 能，query 不受 32 字符限制 | 依赖小程序发布状态，未做 |

落地页的 `onLoad` 同时认这三种：`?code=&anchor=`、`?scene=CHEN2026-10086`、`?scene=code%3DCHEN2026%26anchor%3D10086`。

### POST `/invite/{id}/revoke`

吊销。同时把由它产生的 `edit_scope` 一并置为失效（历史编辑码才可能有）。

## 3. 宗族 family

### GET `/family/{id}/summary`

族信息 + 数据完整度。**无需登录**（配合浏览码使用）。

```json
{
  "id": 5,
  "name": "广信陈氏",
  "surname": "陈",
  "tangHao": "颍川堂",
  "settlePlace": "上饶市广信区茶亭镇",
  "founderName": "陈公讳德昌",
  "founderEra": "明永乐年间",
  "generationPoem": "文章华国诗礼传家",
  "stats": {
    "personCount": 2864,
    "generationCount": 24,
    "livingCount": 1420,
    "branchCount": 5,
    "completeness": 0.62,
    "missingSpouseCount": 87,
    "pendingRevisionCount": 12
  }
}
```

`completeness`（完整度）和 `missingSpouseCount`（待补配偶数）会显示在族首页，**这是一个公开的进度条，也是集体行动的号召**——"咱们家的谱还差 87 位奶奶的名字"。这比任何运营文案都有效。

### GET `/family/mine`

我所属的族 + 我在其中的状态。

> `familyId` 指的是**当前族**。一个账号可以同属多个族（父系谱 + 母系谱），
> 完整列表用 `/family/list`，切换用 `/family/switch`。

### GET `/family/list`

我加入的全部宗族。当前族排第一（端上弹出的切换面板第一项就是"你现在在哪"）。

族被停用的不会列出来，但成员记录不删除——留痕。

**响应**
```json
{
  "code": 0,
  "msg": "ok",
  "data": {
    "currentFamilyId": 1,
    "families": [
      {
        "familyId": 1, "name": "广信陈氏", "surname": "陈",
        "role": 3, "roleText": "族管理员",
        "claimedPersonId": 17, "current": true
      },
      {
        "familyId": 2, "name": "上饶王氏", "surname": "王",
        "role": 1, "roleText": "族人",
        "claimedPersonId": null, "current": false
      }
    ]
  }
}
```

### POST `/family/switch`

切换当前宗族。

只改「当前族」这一个指针，**不动成员关系**——切回来还是原来的角色和认领人。
没加入过的族切不过去：切族不能代替入族。

**请求**
```json
{ "familyId": 2 }
```

**响应**
```json
{
  "code": 0,
  "msg": "ok",
  "data": {
```

### 谱文 articles（2026-10-21 新增）

编修历史、迁徙源流、谱序、凡例这类**长文章**。树回答"我和谁连着"，谱文回答"我们这一族从哪来"——它是族人最常翻的内容，入口在底部导航第三格（**谱文**，2026-11-02 从首页家族卡移上来）。

**权限口径（启明拍板）：**

- **读** = 本族成员（`user_family` 有行）。访客暂不给看；将来要开放给"带浏览码的访客"再单独评估。
- **写** = 房长及以上（按路径里 `familyId` 查 `user_family.role`，不是 `app_user.role`——后者是"当前族"的快照，可能是另一个族的角色）。**直接生效，不走修订审核**：文章不像世系字段容易引发纠纷，卡一道审核只会让房长懒得写。
- **删除 = 软删**（`status=0`）：「家族撤回权」在审计上要有据可查。

**分类是固定枚举**：`1` 谱序 / `2` 编修历史 / `3` 迁徙源流 / `4` 凡例 / `5` 字辈派语 / `6` 其他。同分类可存多篇（历次修谱各一篇谱序）。自由填分类名三个月后必乱，枚举是拍过板的。

#### GET `/family/{familyId}/articles` —— 谱文列表

按 `category, sort_order, id` 排序（老谱目录的顺序，不按时间）。

**响应** `data.items[]`：

```json
{
  "id": 3,
  "category": 3,
  "categoryLabel": "迁徙源流",
  "title": "从饶州府迁广信",
  "excerpt": "明初自饶州府鄱阳瓦屑坝迁入。 二世祖分居灵溪。",
  "sortOrder": 1,
  "updatedAt": "2026-10-21"
}
```

`excerpt` 是压成单行的摘要（≤60 字 + `…`），列表里不该出现整段正文。`category` 过滤可选。

**首页那一栏的两条硬规矩（2026-10-22 补）：**

1. **端上 `load()` 里必须先 `ensureLogin()`。** 2026-11-02 起谱文页是底部导航的一格，可以被冷启动直接点开——那一刻 `globalData.user / familyId` 都还是空的。先补身份再读族，否则会把"还没登录"说成"还没有加入任何家族"（人在族里，页面却说没有）。
2. **列表页 `onShow` 重拉**（首次跳过）：谱文在详情页写，不重拉就会出现"刚写的那篇不在列表里"。

> 2026-11-02 之前那套"首页家族卡拉谱文 + `articlesReady` 守卫"随入口一起下线了：首页不再拉谱文，也就不存在"请求比身份早到"这个问题。**旧笔记不要照抄。**

#### GET `/article/{id}` —— 谱文详情

**响应** `data`：列表条目的全部字段，另加 `content`（原文，纯文本，按空行分段）、`createdBy`、`updatedBy`。

#### POST `/family/{familyId}/articles` —— 新建（理事会成员及以上）

```json
{ "category": 3, "title": "从饶州府迁广信", "content": "明初自饶州府……\n\n二世祖分居灵溪。", "sortOrder": 1 }
```

`content` ≤ 60000 字。分类非法回 `40001`。

#### PUT `/article/{id}` —— 更新（理事会成员及以上）

请求体同新建，全量替换。**直接生效**，响应 `data.autoMerged` 概念不适用（谱文不进修订流）。

#### DELETE `/article/{id}` —— 删除（房长及以上，软删）

删除后列表与详情立即消失（详情回 `40401`），记录仍在表里。响应 `{"id": 3, "deleted": true}`。

**错误**：本组接口所有"无权限"统一回 `40300`；未入族读谱文也是 `40300`（不是 `40100`——人已登录，只是不是这个族的成员）。

### 家族动态 feed（2026-11-02 新增，端上暂未接）

`GET /family/{familyId}/feed?limit=30`

家族内部的"最近谁在动"，给底部导航「动态」那一格用。**端上目前是占位页**（内容口径未定），接口先备好，定了直接接。

**口径**

- **只收已经落地的动作**：`revision.status IN (2 通过, 4 自动合并)`、`family_article.status=1`、`claim.status=2`。待审的修订不进动态——还没成事实，写进"谁补了什么"会让族人以为已经改了。
- **只有本族成员能看**（读 `user_family`，与谱文同门）：动态里有"谁认了哪一位"。
- 三类事件合成一条按时间倒序的流，`key` 形如 `rev-12 / art-3 / claim-1`。

**响应**

| 字段 | 说明 |
|---|---|
| `familyName` | 页面标题用 |
| `items[].type` | `create` 新增人物 / `edit` 补全 / `delete` 删除 / `article` 谱文 / `claim` 认领 |
| `items[].actor` | 行动人（优先谱上姓名，其次微信昵称） |
| `items[].text` | 一句话，端上直接显示（服务端拼好，diff 逻辑不散到端上） |
| `items[].personId` / `articleId` | 点击跳转用，二选一 |
| `items[].at` / `day` | `2026-10-29T17:17:19` / `2026-10-29`（端上按天分组） |

**为什么不建 activity 表**：一个族几十到几百人，三类各取最近 30 条内存合并即可；真到几千条再上（那时也需要真正的消息流模型）。姓名统一走 `project_name` 脱敏，与树接口同一口径。

## 4. 家族树 tree

### GET `/tree/{familyId}` —— 核心接口

两种视图共用，靠 `view` 区分。`lineage`（我的支系）已于 2026-10-21 **退休**：
它想解决的"一次看全一支"在真实规模下不可读，而"逐代下钻"用 `mine` 就能做到。
参数仍兼容，返回结果按房过滤，但端上已无入口。

**参数**

| 名 | 必填 | 说明 |
|---|---|---|
| `view` | 是 | `mine` 焦点视图（**端上渲染为垂直卡片流**，2026-10-28 起）｜ `overview` 全族大宏图（**端上渲染为 Canvas 谱牌树**，2026-10-29 定稿）｜ `lineage` 已退休 |
| `anchor` | view=mine 时必填 | 焦点人物 person_id。**点谁，谁就成为锚点**——这就是逐代下钻 |
| `rev` | 否 | 客户端上次拿到的版本号，一致则返回未修改 |
| `detail` | 否 | `full`（默认，带姓名）｜ `lite`（仅坐标，**只给"未认领时挑锚点"这一发用**；大宏图要显示姓名，不能用 lite） |
| `siblings` | 否 | **仅 view=mine**：同代最多画几个男丁节点（含锚点本人），默认 3；点「还有 N 位」时传 99 展开全部。该值与折叠结果一起进布局缓存键 |

> ### 视图口径（2026-10-21 修订）
>
> 真实冷启动不是"几十人慢慢填"，而是宗祠理事会把老谱拍成照片、OCR 转录进来，
> **开局就是十几代、200 活在世、500+ 节点**。实测 15 代 / 564 人：
> 画布 9528×2136px、2255 个 view、整幅适配后字号 **0.47px**。
> 结论：**不做"一次看全"**。总览只当地图，看清一个家靠焦点视图。
>
> | view | 范围 | 端上技术 |
> |---|---|---|
> | `mine` | 锚点**上 1 代、下 1 代** + **全部配偶（含离异）** + 兄弟姐妹（同代最多 3 个男丁）+ 外孙 2 层 | WXML 绝对定位 |
> | `overview` | **只含 `lineage_role` 1（男丁）/ 2（本族女儿）**，不含媳妇、女婿、外孙 | **Canvas 谱牌树**（2026-10-29 定稿）：节点是 64×72 带姓名的谱牌（2026-11-02 缩牌，一屏横向放下 4 人），正交折线连世代；1:1 不缩放、上下左右平移；左侧一列「世代丁口」固定；点人看详情 |
>
> 两条硬规则：
>
> 1. **配偶永不因离异而隐藏。** 只要这个人是某个孩子的父/母，他/她就出现在那一屏；
>     "离异"只改变卡片框线（虚框）和标注（`已离异`）。把母亲从孩子眼前藏掉，
>     "离婚"在子女视角里就变成了"没有母亲"。
> 2. **夫妻卡片零间距紧贴（`spouseGap = 0`）。** 本人与配偶首尾相接排在一条行上，
>    视觉上是一个不可分的单元；接缝两侧的圆角由端上切平（`flatRight` / `flatLeft`）。
>    **卡片位置不受子女数量影响**——旧实现把配偶卡放在"她那一列"的中心，
>    列被她的孩子撑多宽、人就被推多远，实测妻子离丈夫 220px，看着像两家人。
> 3. **子女按生母分组，不同母亲不混排。** 每位配偶的子女成一组，组按配偶顺序
>    从左到右排；`motherId` 随亲子边下发，端上从生母下垂再折到孩子。
>    分组只保证"同母的孩子在一起"，**不保证孩子正对某个母亲**——卡片贴住之后
>    列中心不再等于卡片中心，这是为"夫妻紧贴"付的代价；换来的是单配偶家庭
>    （绝大多数）孩子整体居中在父母单元之下。
> 4. **离异用虚框，丧偶不用。** `endReason` 1（离异）/ 3（婚姻无效）→ 卡片虚线框；
>    2（丧偶）保持实线，只按"已故"着色。离异的婚姻横梁同样画虚线，人照常留在图上。
>
> `overview` 收窄到直系丁口之后，横向宽度不再随"每位先人有几位夫人"线性膨胀。

**婚姻边与亲子边的附加字段**

```json
// 婚姻边
{ "from": 10020, "to": 10021, "type": 2,
  "unionId": 331, "unionSeq": 2, "unionType": 2, "ended": true, "endReason": 1 }

// 亲子边
{ "from": 10020, "to": 10041, "type": 1, "motherId": 10021 }
```

- `unionSeq`（1、2、3…）决定「元配 / 继配 / 侧室」的先后，端上据此排序，不靠 id。
- `ended` = 有 `end_date` 或有 `end_reason`；`endReason` **1 离异 / 2 丧偶 / 3 撤销**。
  端上把已结束的婚姻边画虚线，**人照常显示**。
- `motherId`：生母在同一屏时下发，端上从她所在的位置起笔、折到孩子；不下发 = 生母未知，从父亲起笔。

**大宏图为什么不用 `lite`：** 大宏图的节点上要写姓名——`lite` 没有名字，画出来等于一片认不出的色块（2026-10-29 实报"只有一个色块占位"）。500+ 节点带姓名的全量 JSON 约 100—200KB，一次请求可接受（有 `rev` 缓存，未变更不回包）。`lite` 只保留给**未认领时挑锚点**这一发（只要坐标和最上面那个人）。

**折叠字段（仅 view=mine）**

兄弟超过 `siblings` 个男丁时，多出来的这一屏不画，但要在响应里说清楚：

```json
"collapsed": { "siblingsHidden": 5, "siblingsTotal": 8 }
```

- `siblingsHidden`：这一屏没画出来的同代男丁数（配偶随他们一起不画）
- `siblingsTotal`：同代男丁总数（含锚点）
- 没有折叠时**不下发这个字段**（不是 `null`，是键不存在）
- 端上把它画成「还有 5 位」角标，点击带 `siblings=99` 重拉

**世代统计字段（仅 view=overview）**

总览不止给形状，还给"每一代有多少丁口"——这是理事会最关心的一句话。

```json
"generationStats": [
  {"gen": 1, "count": 2, "male": 1, "female": 1},
  {"gen": 2, "count": 9, "male": 7, "female": 2}
],
"lineageTotal": 200,
"maleTotal": 132,
"femaleTotal": 68,
"generationCount": 15
```

- **口径：只数 `lineage_role` 1（男丁）和 2（本族女儿）**。
  媳妇、女婿、外孙是外姓，计进去会让规模虚高一倍，也和理事会手里的老谱对不上。
- `gen` 是世次（从 `family.first_gen_label` 起算），`count` 是该代丁口数
- `male` / `female` 是这一代的男丁数与本族女儿数，`count = male + female`
- 端上刻度的文案就是按这个拼的：**`第4世 2人（男1 女1）`**
- 端上用它在 Canvas 左侧画"第 N 世 · N 人"刻度，右上角显示"15 代 · 200 丁口"
- 这个数字**必须服务端算**：端上为了性能少画几代时，报出去的人数就会跟着错

### GET `/person/{id}/missing` —— 待补全清单 ⭐

**这是"接力修谱"的核心接口。**

传统做法是给用户一张 20 个字段的表，用户看一眼就退出去了。这个接口换个角度：**先算出"这个人周围还缺什么"，再只问这几个问题。**

```json
{
  "personId": 10020,
  "missingCount": 3,
  "items": [
    {
      "key": "father",
      "label": "您的父亲",
      "question": "您父亲叫什么名字？",
      "type": "create_person",
      "prefill": { "surname": "陈", "generation": 18 },
      "required": ["name"],
      "optional": ["birthDate", "livingStatus", "burialPlace"],
      "reason": "家谱中尚未记录您父亲"
    },
    {
      "key": "mother_name",
      "label": "您母亲的名字",
      "question": "您母亲的名字是？",
      "type": "update_field",
      "targetTable": "person",
      "targetId": 10021,
      "field": "name",
      "prefill": { "surname": "李" },
      "displayBefore": "配李氏",
      "hint": "老谱上只记了姓，补上名字后她就不再是\"李氏\"",
      "reason": "家谱中仅有姓氏，缺姓名"
    },
    {
      "key": "spouse",
      "label": "您的配偶",
      "question": "您的配偶叫什么名字？",
      "type": "create_union",
      "prefill": { "partnerAId": 10020, "unionType": 1 },
      "required": ["partnerName"],
      "optional": ["marriageDate"],
      "reason": "家谱中尚未记录您的婚姻",
      "skippable": true,
      "skipLabel": "未婚 / 暂无配偶",
      "skipHint": "记为「未婚」，之后不再追问"
    }
  ],
  "completedCount": 2,
  "totalCount": 5,
  "nextAfterComplete": { "hint": "填完后，系统会检查您子女的信息" }
}
```

**设计要点：**

- `question` 是一句**具体的中文问句**，不是字段名。用户看到的是"您母亲的名字是？"，不是"配偶姓名"。
- `displayBefore` 让用户看到改动前后的对比（`配李氏` → `李秀英`），**这个视觉冲击是产品最强的情绪点**。
- 响应另带 `completeness`（0~1）：**与 `missingCount` 同一套口径**——适用项才计分（未成年不计配偶、第 1 世不计父亲、**媳妇/女婿/外姓不问父母**、生平不参与），因此 `missingCount == 0 ⟺ 完整度 100%`。端上的进度条和"还差 N 项/已经完整了"两个显示不会打架。
- `reason` 说明为什么问这个，用户不反感被问，反感的是不知道为什么被问。
- 一次只展示 1—3 个任务，做完再出下一批。**清单不能一次给 20 条，那是待办，不是引导。**
- `skippable` + `skipLabel`：这一问允许回答"没有"。**没有 `skipLabel` 的跳过只是"以后再说"**（不落库，下次还问）；有 `skipLabel` 的跳过是**一次真正的回答**，端上按钮文案直接用这个字段，不要写死"以后再说"。
- **外孙任务与女儿本人答案的联动**：女儿名下已有子女记录、或她本人声明过「暂无子女」（`childless=1`），父母这边的外孙任务自动消失——事实已经确认，不必父母代答。**「未婚」不触发**：未婚 ≠ 无子女，这一问照旧。目前三处：`spouse` → 落 `maritalStatus=1`（未婚）、`children` → 落 `childless=1`（暂无子女）、`external` → 落 `externalOptOut=1`（外孙不入谱）。**新增可跳过任务时必须同时给一个落库字段**，否则它会变成一个永远补不完的缺口。
- **权限：`viewer.can_edit(id)` 才放行，否则 40300。** 判据必须与详情页的 `pending`、树节点的 `hasPending/badge`、首页底部条的 `pending` **完全同一个谓词**。曾经这里卡在"本人或房长"，而写权限（`edit_scope`）更宽——房长给直系签了编辑权，却不让他看缺什么，页面上还照样显示缺口数字，点进去 40300。**能补的人才看得见缺口，看得见缺口的人一定补得了**，这是同一个开关的两面，不能各判一套。
- `canSubmit` 与 `missingCount` 同源：看得见清单 ⟹ 能提交。范围外的改动不走这里，走 `PATCH /person/{id}` 的修订通道。
- 「都补上了」这句话只能由服务端说。端上答完最后一条时，必须重新请求本接口、拿 `missingCount` 出文案，**不许凭本地队列空了就宣布补齐**——用户点「以后再说」是不落库的，端上却记成"答过了"，于是补全页说"补完了"、回到详情页还是"还差 1 项"。同类"同一件事算两遍"已经复发四次（67% → 底部条 → 节点角标 → 补全页）。
- **数字和人是绑定的。** 任何显示"还差 N 项"的地方（详情卡片、树上角标、首页底部条）都必须同时说清 **N 是谁的**；对应的「去补全」只能跳那个人。2026-10-21 的实报就是反面教材：底部条的数字来自锚点（吴敏），按钮却固定跳 `claimedPersonId`（陈启华），于是"条上说吴敏还差一项、点进去说陈启华已补全"——两个页面都"算对了"，说的是两个人。

### POST `/person/{id}/missing/submit` —— 回答一条待补全任务

```json
{ "key": "spouse", "values": { "partnerName": "李秀英" } }
```

回答"没有"：

```json
{ "key": "spouse", "skip": true }
```

`skip` 只在任务带 `skippable: true` 时接受，落库的是**事实字段**，不是"已跳过"标记：

| `key` | 落库 | 语义 |
|---|---|---|
| `spouse` | `person.marital_status = 1` | 未婚 |
| `children` | `person.childless = 1` | 本人确认无子女 |

**为什么值得单独一条接口说明**：配偶原本是必填项，未婚的人只有两条路——编一个名字（谱里凭空多出一个不存在的人，几十年后没人分得清真假），或者永远卡在进度条上。答"没有"之后，待补全清单与完整度的分母**同时**把这一项排除，否则会出现"答了、清单空了、进度还是 80%"。

### POST `/person` / PATCH `/person/{id}`

**新增或修改人物。都不直接落库，而是写入 `revision` 表进入待审队列。**

**请求（PATCH）**
```json
{
  "fields": { "birthDate": "1965-03-12", "occupation": "教师" },
  "generationName": "国",
  "submitNote": "本人填报",
  "idempotencyKey": "a1b2c3d4-xxxx"
}
```

**响应**
```json
{
  "revisionId": 3021,
  "status": 1,
  "statusText": "待审核",
  "generationHint": {
    "matched": false,
    "expected": 18,
    "found": 19,
    "char": "国",
    "level": "info",
    "message": "按字辈诗「文章华国诗礼传家」，'国'字应为第 18 世，您填写的是第 19 世，请确认是否无误",
    "blocking": false
  },
  "previewEffect": "提交后：陈国栋 的出生日期 由「1965年」变为「1965年3月12日」"
}
```

**`generationHint.blocking` 恒为 `false`。** 决策第 1 条定的"只做提示参考，不做强制校验"，在接口层就体现为这一个字段——它永远不阻断提交。客户端把它渲染成黄色信息条，用户点"确认无误"继续走流程。

**`idempotencyKey`**：用户在小程序里网络抖动时容易重复点提交。用幂等键保证同一次提交只生成一条修订。

我提交过的，按状态分组。**用户提交完能立刻看到"待审核"的条目，这个反馈很重要**——否则用户不确定自己填的东西到底存没存进去。

```json
{
  "total": 12,
```

`submitterRelation`（提交人是被改对象的什么人）会大幅提升审核效率——**房长看一眼"之子"，基本就能判断可不可信。**

### GET `/revision/{id}`

单条修订详情，含前后快照。

### POST `/revision/{id}/approve` / `/reject`

```json
{ "reviewNote": "与户口本一致", "applyToConflict": true }
```

通过后：落库 → `family.data_rev + 1` → 相关布局缓存失效 → 给提交人发通知。

**批量通过**：`POST /revision/batch-approve`，body 传 id 数组。首期导入期房长可能要审几百条，单条点会崩溃。

### POST `/revision/{id}/withdraw`

提交人自己撤回。

### POST `/revision/{id}/resolve-conflict`

冲突解决。两条修订改了同一字段的不同值时：

```json
{ "keepRevisionId": 3021, "rejectRevisionId": 3035, "note": "已电话确认，以启明填写的为准" }
```

**注意：这个动作只有房长/管理员能做，且必须填 `note`。** 平台不替宗族做辈分判断，只提供工具和留痕。

```json

  "claimId": 12, "personId": 14, "personName": "陈思远",
```

### POST `/admin/identify/unlock` —— 解除答题限速（理事会成员及以上）

```json
{ "familyId": 1, "userId": 2, "note": "家人代答试错，解禁" }
```

只能解本族的人（按 `user_family` 或认领节点判定），写 AuditLog（`action=identify.unlock`）。

**限速规则（2026-10-29 修订）**：滑动窗口 1 小时，每小时最多 10 次，连续 **真答错** 5 次冷却。`40901 节点已被他人认领`、`已故祖先`、`重名需补填` 这类**系统态/信息不足一律记 neutral，不计入失败**——用户答案可能全对，错在系统状态，不该罚他。被限速的响应（42900）`data` 带 `retryAfterSeconds / reason / failCount / unlockable`，端上据此显示「还要等约 N 分钟」。

### POST `/admin/person/merge`

**合并重复人物。** 老谱导入必然产生重复（同一人在不同房重复记录、同一人在两卷书里写法不同）。

```json
{
  "sourcePersonId": 10086,
  "targetPersonId": 10099,
  "mergeStrategy": {
    "name": "target",
    "birthDate": "source",
    "biography": "concat",
    "relations": "union"
  }
}
```

合并后 `sourcePersonId` 不删除，置 `status=0` + `merged_into_id=target`，**保留全部溯源能力**。家谱合并是最容易出错的操作，必须有完整的回滚路径。

### POST `/admin/role` —— 授予 / 调整成员角色（族管理员）

```json
{ "userId": 10086, "role": 2 }
```

`role`：1 族人 / **2 理事会成员（含房长）** / 3 族管理员。

**角色定位（2026-10-22 拍板）：2 号角色叫「理事会成员」。** 真正的房长年纪大、
不操作智能机，实际用后台的是理事会里会用手机的年轻人——房长授权他们代管，
语义上仍含房长本人。**角色不是认领来的，是指定的**：认领解决"树上这个人是我"
（`claimed_person_id`），角色解决"我管多大范围的事"（`user_family.role`），两条线。

防线：① 只有族管理员及以上能调（房长不能互相提权）；② 不能授予比自己高的角色；
③ 不能降低自己的角色（防手滑把自己降成族人，全族锁在后台外面）；④ 非本族成员不能授。

双写规则与 family_member 同源：`user_family.role` 是真相，目标用户若正停在本族，
`app_user.role` 快照同步回填——否则端上拿到旧身份，权限忽有忽无。

### POST `/admin/tree/rebuild`

强制重算指定视图的布局缓存。用于数据修完之后。

### POST `/admin/person/batch-import`

批量导入（家谱 OCR 工具的落地点）。

```json
{
  "familyId": 5,
  "mode": "dryRun",
  "sourceType": 3,
  "payload": { },
  "options": { "autoMerge": false, "skipRevision": true }
}
```

**必须支持 `dryRun`。** 导入 5000 条数据前，先让运营看一遍"将会新增 4800 人、合并 120 人、有 15 条疑似重复"，确认无误再真跑。**没有 dryRun 的批量导入工具，一定会出事。**

### 新增人物（`POST /v1/person`）的挂载方式

新增必须挂到一个已有节点下，服务端用 `relation` 里的锚点判定"你对谁有编辑权"：

| `relation.type` | 锚点字段 | 含义 |
|---|---|---|
| `child_of` | `parentId` | 给某人添子女 |
| `spouse_of` | `partnerId` | 给某人添配偶 |
| `father_of` / `mother_of` | `childId` | 给某人添父母（锚点是**那个孩子**） |

`fields` 至少要给 `name` 或 `surname`。端上直接补录时要连 `gender`、`lineageRole`、`generation` 一起传，少传不会报错，但会静默写错：

- `lineageRole`（1 男丁 / 2 本族女儿 / 3 媳妇 / 4 女婿 / 5 外姓）决定他算不算本族丁口。
  不传一律按 1 算，于是娶进来的媳妇会被数进"男丁人数"，而且全族树的筛选口径也跟着错。
- `generation` 不传时，布局兜底成第 1 世 —— "给爷爷补父亲"会把老爷子摆到始祖旁边。
- 返回 `data.autoMerged`：`true` 表示已直接生效，`false` 表示进了待审队列。

## 9. 给 OCR 工具的接口约定

第二个工作（家谱图片 → 数据）的输出**必须严格对齐这三个结构**，否则导入环节会非常难受：

```json
{
  "meta": { "familyId": 5, "sourceNote": "光绪十八年陈氏宗谱 卷三", "ocrVersion": "1.0" },
  "persons": [
    {
      "tempId": "p_001",
      "name": "陈国栋", "surname": "陈", "gender": 1,
      "generation": 19, "generationName": "国",
      "courtesyName": "文山",
      "birthDate": "1965-03-12", "birthDatePrecision": 3,
      "livingStatus": 1,
      "sourceType": 3, "sourceNote": "卷三 第十二页 左",
      "confidence": 2,
      "altFamilyId": null,
      "bbox": [120, 340, 260, 400]
    }
  ],
  "unions": [
    { "tempId": "u_001", "partnerATempId": "p_000", "partnerBTempId": "p_002", "unionType": 1 }
  ],
  "parentChild": [
    { "tempId": "pc_001", "unionTempId": "u_001", "childTempId": "p_001", "relation": 1, "isPrimary": 1, "isBiological": 1, "seq": 1 }
  ],
  "unresolved": [
    {
      "type": "name_unknown",
      "rawText": "配王氏",
      "targetTempId": "p_003",
      "suggestion": "只识别到姓氏，建议标记为待补全",
      "bbox": [300, 340, 360, 400]
    }
  ]
}
```

**`tempId` 机制**：OCR 阶段还没有数据库 ID，用临时 ID 表达关系，导入时由后端做 ID 映射。这是批量导入的标准做法，能保证关系不乱。

**`bbox`（原图坐标框）**：记录每个人物来自原图的哪个位置。**这个字段的价值在于"可回溯"** ——导入后族人在小程序里看到一条可疑记录，可以点开看原谱那一段的截图，自行判断对错。这是"数据可信度"的最终保障，极其重要，OCR 阶段一定要保留。

**`unresolved`**：识别不了的一律不猜，列出来交给人工。宁可少导入，不可导入错的。**家谱数据的错误会被后代当成祖上记载沿用几十年。**
