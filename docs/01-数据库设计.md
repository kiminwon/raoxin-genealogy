## 一、先讲三个"为什么"，这决定了整张表的形状

### 1. 为什么不能用 `father_id` / `mother_id`

这是最容易被低估的设计点。看起来存父子关系只要两个字段，但家谱里有一类情况会让它彻底失效：

> 陈国栋生于 1965 年，本生父是长房的陈文山。1972 年长房无嗣，国栋被过继给三房的陈文海为嗣。
> 那么他的 `father_id` 填谁？

填文山（本生父），三房这边就断了，家谱上三房绝后；
填文海（嗣父），长房这边也断了，而且他和他亲兄弟的关系消失了。

再婚同理：一个人的孩子来自两段婚姻，`mother_id` 只有一个位置，第二个孩子就没法归位。

**所以关系必须拆成两层：**

- `family_union` —— "哪两个人组成了一个生育单元"（含婚姻类型、起止）
- `parent_child` —— "这个单元里的哪个孩子，以什么身份进来"（亲生/过继/收养）

两层拆开后，过继只需要给同一个孩子挂**两条** `parent_child`：一条挂在生父的 union 下（`relation=亲生, is_primary=0`），一条挂在嗣父的 union 下（`relation=过继, is_primary=1`）。树里显示在嗣父下面，人物详情里标一行"本生父：陈文山"。这是传统家谱的标准写法，数据模型也能表达。

### 2. 为什么 `family_union` 的第二个伴侣可以为空

老谱里满篇是"配某氏"——只知道娶了个人，不知道是谁。如果 union 表强制要求两个伴侣都存在，这一大类记录就存不进来。

所以 `partner_b_id` **允许为 NULL**，含义是"配偶存在但信息不详"。同时也覆盖了未婚生育的场景。

另外约定：**`partner_a_id` 永远是"承袭世系的一方"**（通常是父方；女儿招赘时就是女儿本人）。这样从孩子回溯父亲的查询是一条直线，不用判断性别。

### 3. 为什么 `person` 表会装进外姓人

传统家谱的"人"表只放同姓男丁。但决策第 2 条定了"女儿入谱、外孙可选入谱"，一旦同意这件事，`person` 表里必然出现姓王的、姓李的。

这不是设计缺陷，是必然结果。所以给每个人打一个 `lineage_role` 标签，**用于判断"在哪张视图里出现"，而不是判断"是不是这家人"**：

| `lineage_role` | 含义 | 全族树 | 我的一家 |
|---|---|---|---|
| 1 本族男丁 | 承袭世系的同姓男丁 | ✅ 显示 | ✅ 显示 |
| 2 本族女儿 | 本族出生的女性 | ✅ 显示 | ✅ 显示 |
| 3 媳妇 | 嫁入本族的女性 | ✅ 显示（挂在丈夫旁） | ✅ 显示 |
| 4 女婿 | 本族女儿之夫 | ❌ 不显示 | ✅ 显示 |
| 5 外姓后代 | 外孙及其子孙 | ❌ 不显示 | ✅ 显示（限 2 层） |

**全族总览 = `lineage_role IN (1,2)`。** 只画直系丁口（男丁 + 女儿）；媳妇、女婿、外孙都不进——既落实了决策第 2 条"外孙在全族不做展示"，也避免"200 人的族报出 400 人"（媳妇能占一半，报出去跟理事会对不上账）。媳妇仍然要进树，但只在某人成为锚点时，出现在他那一屏「我的一家」里（见决策 16：配偶永不因离异而隐藏）。

**媳妇 / 女婿 / 外姓的 `parent_child` 永远为空，这是正常的，不是缺数据。** 他们的父母记在娘家的谱上。所以待补全清单**不对这三类人问父母**：否则每位嫁入的媳妇都会永久挂一条"您父亲叫什么名字？"——答了会把外姓父亲挂进本族世系（全族树里凭空长出一支外姓人），跳过则任务不落库、下次照旧问，于是"还差一项"永远消不掉。完整度的分母同步排除这一项（否则 0 项缺口也只显示 67%）。

## 二、"我的一家"到底包含谁

这是产品的第一屏，也是唯一需要在手机上保持可读的树。范围必须卡死，不然会膨胀成第二张全族图。

**以锚点为中心，只取紧邻的一代：**

| 方向 | 范围 | 数量估算 |
|---|---|---|
| 向上 | 父、母（1 代） | 2 |
| 向下 | 子女（1 代，**按生母分组**，同母成组不混排） | 2—6 |
| 横向 | 配偶（多段婚姻全部列出） | 1—6 |
| 横向 | 本人的兄弟姐妹（默认 3，可展开到全部） | 3—8 |
| 扩展 | 女儿的配偶 + 外孙（2 层，只在此视图显示） | 约 2—4 |
| **合计** | | **12—25 个节点** |

**为什么只给一代：**

- 竖屏一屏能清晰容纳的层级大约是 3—4 层，但"塞得下"和"读得懂"是两件事：每代人数一多就必须缩字号，实测 4 代就已经挤成一团
- 情绪上，用户第一眼只需要确认三件事：我是谁、我父母是谁、我孩子是谁。曾祖以上多数人已经叫不出称呼，放在第一屏是噪音
- 想往上看就**换锚点**：点画面上最上面那位，他成为新的中心，视图跟着移动一代；往下同理。全族的形状去「全族大宏图」——它是一张带姓名的谱牌树（只含直系丁口，节点 64×72、名字常显、1:1 可平移），既回答"我们家有多大"，也回答"这个人在第几世"

## 三、表结构说明

完整建表语句见 `schema.sql`。以下是每张表的职责与关键字段的取舍说明。

### 3.1 `family` 宗族

一棵树对应一条记录。除了基本信息，有两个字段值得说：

**`generation_poem`（字辈诗）+ `first_gen_label`（字辈起始世次）**

字辈诗是一串字，第 i 个字对应 `first_gen_label + i` 世。比如"文章华国诗礼传家"、起始世次 15，那么"国"字对应第 18 世。

决策第 1 条说"只做提示参考，不强制"。落到实现上就是：**校验逻辑不写在数据库约束里，写在录入接口的返回值里。** 用户提交时后端算一次，返回：

```json
{ "generationHint": { "matched": false, "expected": 18, "found": 20, "char": "国", "level": "info" } }
```

前端把这个当**黄色提示条**展示："按字辈诗，'国'字应为第 18 世，您填的是第 20 世，请确认。" 用户点"仍然提交"就照常入库。

**为什么不能强制：** 你说得对，现在起名越来越不看字辈。而且强制校验会误伤三类人——女性成员（基本不用字辈）、外姓成员（字辈诗根本不同）、以及文革期间改名的那一代。一旦出现"系统不让我录我爷爷"，用户直接弃用，这比数据有小错严重得多。

**校验只在 `lineage_role=1` 且 `generation_name` 有值时才跑。** 也就是说，只有当用户主动填了"字辈用字"这个字段，系统才比对。不填就完全不打扰。这样既不失灵，也不烦人。

**`data_rev`（数据版本号）**

家族数据每次变更 +1。树的布局缓存靠它判断是否失效。理由见 3.11。

### 3.2 `person` 人物

字段最多的一张表，分五组：谱系定位 / 姓名 / 生卒葬 / 社会信息 / 元数据。

**`name` 允许为 NULL —— 这是刻意的。**

老谱里"配王氏"占相当比例。如果我们强制姓名非空，录入员就只能编一个或者填"王氏"，前者是造假，后者是脏数据。正确做法是：

- 只知道姓 → `surname='王'`，`name=NULL`，界面显示"王氏"
- 完全不知道 → 两个都 NULL，界面显示"配某氏"
- **并且自动进入「待补全清单」**，由后代去补

这一点接上了产品的核心机制：**每一条"配某氏"都是一个待办任务，而不是一条残缺数据。** 老谱导入进来之后，系统会自动生成几十上百条"补全奶奶的名字"的任务，分发给对应的后代。这是"接力修谱"最有力的第一批弹药——它比让用户凭空填表要具体得多，也更容易打动人（"让你奶奶的名字出现在家谱里"）。

**`generation` 与 `lineage_role` 的关系**

外姓人（外孙）也会填 `generation`（= 母亲世次 + 1），但**仅用于"我的一家"里的定位排布**，不参与字辈校验、不进入全族树的层级计算。

**`is_lineage_carrier`（是否承袭世系）**

这个布尔值决定"全族树的纵向主链从这里继续往下走吗"。

默认规则（应用层实现）：

| 情况 | 默认值 | 理由 |
|---|---|---|
| 本族男丁（role=1） | 1 | 父系主链 |
| 本族女儿（role=2）+ 招赘婚 | 1 | 孩子随母姓入本族，她要接下去 |
| 本族女儿（role=2）+ 出嫁 | 0 | 孩子进别人家的谱 |
| 媳妇（role=3） | 0 | 她是配偶，不作为世系起点 |
| 女婿 / 外孙（role=4/5） | 0 | 不进全族主链 |

用户可以手动改——比如招赘但孩子仍随父姓，那就把女儿设成 0。**我们把判断权留给用户，只给一个符合常规的默认值。**

**`alt_family_id`（预留字段）**

决策第 3 条：首期不做跨树，但预留。

将来做母系功能时，这条字段会升级成一张中间表 `person_family_membership(person_id, family_id, relation_type, is_primary)`，支持"一个人在多个族谱里有位置"。现在先放一个字段占位，**成本为零，但避免了将来改主表**——改主表意味着全量数据迁移 + 所有查询重写，那是几天的活；加个字段是几秒钟的活。

**`privacy_level` + `living_status`**

脱敏的实际执行放在 API 层（不是数据库视图），原因在下一节讲。

**`marital_status` + `childless` + `external_opt_out`（2026-10-21 新增）**

这三个字段回答的是同一个产品问题：**"没有"要能说出口。**

配偶原本是必填项，未婚的人只有两条路——编一个名字，或者永远卡在待补全清单里（进度条停在 80% 下不来）。而"编一个"比"空着"糟得多：谱里会凭空多出一个不存在的人，几十年后没人分得清哪条是假的。

| 字段 | 取值 | 语义 |
|---|---|---|
| `marital_status` | 1 未婚 / 2 已婚 / 3 丧偶 / 4 离异 / NULL | NULL = 未确认，会继续问 |
| `childless` | 0 / 1 | 1 = 本人已确认没有子女 |
| `external_opt_out` | 0 / 1 | 1 = 已明确「外孙不入谱」，不再追问这位的女儿所出子女 |

三个要点：

1. **它们是事实，不是"用户点了跳过"的标记。** 老谱写"未娶""无嗣""外孙不列"，本来就是一句正经记载；将来查谱，"未婚"这两个字有信息量，"已跳过"没有。
2. 有 `family_union` 记录时以 union 为准，这两列只用来表达"明确没有"。
3. 待补全清单与完整度**必须同口径**读它们：`_check_spouse` / `_check_children` / `_check_external` 见到就早返回，`_person_completeness` 的分母同步把这一项排除。否则会出现"答了未婚、清单空了、进度还是 80%"——那正是 67% 那类矛盾的同一个病根。

**`external_opt_out` 挂在谁身上：** 挂在**提问的人（父/母）**上，不是逐个女儿。家谱里"外孙入不入谱"讲的是一支的规矩，不按"这个女儿记、那个女儿不记"来定。没有这一列时，外孙任务是唯一一类"点了以后再说却没地方落库"的任务——跳过只是端上本地跳过，服务端照旧记着，每次进来都问一遍，完成度永远上不去。

### 3.3 `family_union` 婚姻单元

**注意：物理表名叫 `family_union`，不叫 `union`。**

`UNION` 是 SQL 保留关键字，表名叫 `union` 的话，所有 SQL 都必须写成 `` `union` ``，一旦哪处漏了反引号就是语法错误，而且报错信息往往指向别的位置，排查很烦。同理 `user` 表改名 `app_user`（避免和 `mysql.user` 系统表及 `USER()` 函数混淆）。

设计概念上它仍然是"Union（婚姻单元）"，只是物理命名避开了关键字。

`union_type` 覆盖：初婚 / 再婚 / 纳妾 / 入赘 / 招赘 / 未婚生育 / 不详。

**纳妾要不要单独列类型：** 要。老谱里"继配""侧室""副室"是明确记载的，直接归成"再婚"会丢失史料信息。但我们只记录，不做任何价值判断，界面上用中性词"第二配偶"呈现。

`partner_b_id` 为 NULL 的处理见前文。

### 3.4 `parent_child` 亲子关系

`relation` 枚举：亲生 / 过继（嗣）/ 收养 / 继子女 / 随母 / 不详。

`is_primary` —— 一个孩子有多条记录时，哪条是"主谱关系"（决定他显示在谁的下面、算哪一世）。过继场景：嗣父那条 `is_primary=1`。

**过继不需要用户额外操作。** 录入界面就是一句人话："这个孩子是本生的，还是过继来的？"选"过继"之后再问一句"过继给谁"，系统自动生成两条记录。**用户不需要理解 `is_primary` 是什么。**

### 3.5 `app_user` 微信用户

`openid` 唯一。`claimed_person_id` 存认领结果（NULL 表示还没认领）。

**关于 `phone_enc`（手机号密文）——这里要澄清一个区分：**

你同意的脱敏口径是"人物数据里不采集住址和手机号"。这条我完全照办：`person` 表里**没有** `phone` 和 `address` 字段，一个都没有。

但 `app_user`（账号表）里我保留了 `phone_enc`，因为它是**账号身份核验信息，不是家谱史料**：

- 认领审核需要它——二叔说"我是陈国栋"，管理员总得有个东西核实
- 后续"你提交的修改被驳回了"这类通知也需要触达通道
- 它以密文存储，**不参与任何家谱查询，不进树、不进详情页、不对任何族人展示**

两者是完全不同的东西：一个是"家谱里关于这个人的记载"，一个是"这个账号背后是谁"。混为一谈会导致认领环节没法做。

如果你觉得连这个也不要，删掉该字段即可，认领审核改成纯人工（由房长线下核实后手动通过），功能不受影响——只是审核工作量会上去。

### 3.6 `user_family` 账号与宗族的成员关系（多族）

2026-10-17 新增。原来 `app_user.family_id` 一列表示"我属于哪个族"，一人只能有一个。
可父系谱和母系谱都要查——第二个族一出现，一列就装不下了。

| 列 | 说明 |
|---|---|
| `user_id` + `family_id` | 唯一键，一行 = 一个人在某个族 |
| `role` | **本族内**的角色（1 族人 / 2 理事会成员 / 3 族管理员）。他在 A 族是理事会成员、在 B 族是普通族人，互不影响 |
| `claimed_person_id` | **本族内**认领的节点。父系认领"陈雨欣"、母系认领"王某某"互不覆盖 |
| `status` | 1 正常 / 2 已退出 |
| `last_active_at` | 最近一次切到本族的时间，切换面板按它排 |

**2 号角色的定位（2026-10-22 拍板）：「理事会成员（含房长）」。** 真正的房长
年纪大、不操作智能机，实际用后台的是理事会里会用手机的年轻人——房长授权他们
代管，语义上仍含房长本人。**角色不是认领来的，是指定的**（`POST /admin/role`，
族管理员操作）：认领解决"树上这个人是我"，角色解决"我管多大范围的事"，两条线。

**关键取舍：`app_user` 的 `family_id` / `role` / `claimed_person_id` 没删，只降级成"当前族快照"。**

全站鉴权（`build_viewer`、写权限判定、房长门禁）读的都是这三列的当前值。
切族时由 `app/services/family_member.py::activate()` 把三列回填成目标族的值，
于是加多族**一行鉴权代码都不用改**。

代价是「当前族」必须由后端原子切换，不能让端上自己算；任何直接写
`app_user.family_id` 的地方都是 bug，一律走 `join()` / `activate()` / `set_claimed()`。

**为什么不做"退出某个族"**：账号解绑 ≠ 抹掉历史。已通过的认领记录是审计证据
（证明这个人当时答对过父母名字），出纠纷时要能查。首期只做"加入"和"切换"。

### 3.7 `claim` 认领申请

`claim_type`：新建本人节点 / 认领已有节点。

`evidence`：用户自述佐证，比如"我父亲是陈国栋，我生于 1988 年"。这是给审核人看的，不做自动校验。

`status` 里的 `5 冲突` 很重要——**当两个用户同时声称是同一个节点时**，不是简单的"先到先得"，而是标为冲突并通知双方 + 房长。这条路径必须留出来，否则会出现"我认领我自己，系统说这个节点已经被我堂弟占了"这种让人极其恼火的情况。

### 3.8 `invite_code` 邀请码（决策第 5 条，2026-10-22 修订）

**现在只有一种在用的码：族级浏览码（`code_type=1`）。编辑码（`code_type=2`）已停止签发**，只保留对历史记录的兼容（已被接受的授权照旧生效，新码一律回 `40001`）。

| | 浏览码（type=1，在用） | 编辑码（type=2，已下线） |
|---|---|---|
| 谁生成 | 族管理员（`POST /invite/generate`）；族里没有码时，任何族人读 `/family/mine` 也会懒生成一个 | ~~任意已认领族人~~ |
| 锚点 | 无（族级）。**分享时由链接的 `?anchor=` 携带** | `anchor_person_id`（签发者自己） |
| 能做什么 | 看脱敏的全族树；**不带任何写权限** | ~~看 + 编辑锚点周围指定范围~~ |
| 用在哪 | 家族群扩散、一对一分享 | ~~一对一发给直系亲属~~ |

**为什么下线编辑码**（2026-10-22 拍板）：

1. **权限不该由链接携带。** 写权限本来就绑在 `viewer.can_edit(pid)`（`edit_scope`），而 `edit_scope` 唯一正常的来源是**认领**。编辑码试图让"链接带权限"，等于在身份系统之外开了一条查不到人的写权限后路——谁拿码谁都能写，出了事查不到人。
2. **代录需求不需要它。** 理事会成员（`role=2`）本来就全族可写；志愿者分房录入走角色 + `POST /admin/grant-scope`，可追溯、可撤销。
3. **实测它一次都没被用过。** 本地与云端 `invite_code.used_count` 全为 0，`edit_scope` 里 `source=2` 的授权行一条都没有。生成它的前提（已认领）本身就自动带来了更宽的直系范围（`close_relatives(up=2, down=2)`，含兄弟姐妹及其配偶），而它上 3 代却不含兄弟姐妹——增量只有曾祖辈，那一辈通常由理事会统录。

**个人分享保留下来，作用只剩一个：锚点。** 分享路径是 `?code=<族码>&anchor=<分享人 personId>`：对方**点开直接进族**（不用手输家族码），未认领时「我的一家」先聚焦到分享人身上。锚点只是视角，不是权限——它能改什么仍由他自己认领后的 `edit_scope` 决定。服务端在 `accept` 时校验锚点属于本族后回传，端上不必只信 URL。

**历史编辑码的 `scope_rule` + `scope_person_ids` 双存仍然有意义**（老码还在用）：

- `scope_rule` 是规则，如 `{"up":3,"down":2,"spouse":true,"siblings":false}`
- `scope_person_ids` 是**签发那一刻按规则算出来的具体节点 ID 列表**，存成快照

为什么要存两份？这是这张表最重要的设计判断。

**如果只存规则、每次访问动态算：** 树一旦被别人改动（比如有人错误地把你堂叔挂到了你爷爷下面），你的"向上 3 代"范围会**自动扩大**到你堂叔那一家。你没有做任何操作，权限却变大了。反过来，如果节点被误合并，权限会莫名缩小。

**如果只存快照：** 稳定、可审计，但树正常增长后（你新添了儿子），你需要手动重新授权才能编辑自己的儿子。

**所以两份都存：**

- 鉴权时用 `scope_person_ids` 快照 —— **权限只能通过显式动作产生，不会因为别人的编辑而漂移**
- 出现"新节点不在我的快照里"时（你新添了儿子），系统提示"该节点不在您的授权范围内，点击申请扩展"，走一次一键确认 —— 成本很低
- 管理员可以按 `scope_rule` 重算并刷新快照，用于批量修复

这是我在这套设计里最强的一个主张：**权限宁可偏紧，不能偏松。** 权限偏紧的代价是用户多点一次按钮；权限偏松的代价是家谱数据被改坏，而且没人知道是谁改的——家谱数据的信任一旦破坏，整个产品就没有存在意义了。

### 3.9 `edit_scope` 可编辑范围

认领通过后为每个用户生成一行或多行授权记录（历史编辑码被接受时也会，`source=2`）；理事会成员与族管理员按角色直接放行，不必逐节点授权。

`source`：1 认领自证 / 2 历史邀请码 / 3 房长授权。

这张表是鉴权时的**主查询表**——每次写操作前查一次"这个用户对这个人有没有授权"，命中才放行。它是实体表而不是动态计算的，理由同上。

### 3.10 `revision` 修订记录

**所有写操作都以"提交修订"的形式进入这张表，不直接改 person。**

这是"先审后发"还是"先发后审"的问题。我的选择是：**V1 用先审后发**（写入即待审，管理员通过后才落库）。

理由：首期只有一个宗族、数据量小、管理员盯得住。而家谱数据的特点是一旦出错，错误会被后代当作"祖上记载"沿用几十年——**试错成本极高，宁可慢**。

代价是用户提交完要等审核，体验有延迟。缓解办法：用户能立刻在"我的提交"里看到自己填的内容（标记为待审状态，在树上以虚线框显示），不用等审核就能看到成果。

`conflict_with_id`：两条修订改了同一个字段的不同值时，互指，界面上提示双方"您和陈某某对同一字段填写不一致，请线下确认后由一方撤回"。**平台不做裁判，这是宗族内部的事。**（辈分争议我们绝对不能替他决定，这是项目最大的合规与伦理风险点。）

`before_snapshot`：存变更前快照，用于回滚。家谱被改错了一次，得能退回去。

### 3.11 `branch` 支系（房）

房名、房始祖、排序。轻量表。

`founder_person_id` 指向 person，形成循环引用——这也是不加物理外键的原因之一。

### 3.12 `tree_layout_cache` 布局缓存

存三种视图算好的节点坐标。

关键字段 `family_rev`：生成缓存时记录当时的 `family.data_rev`。请求进来时如果 `cache.family_rev < family.data_rev`，说明数据变了，重算。

**为什么要缓存：** Reingold-Tilford 是 O(n) 的算法，几千个节点算一次大概几十到几百毫秒。单次不算慢，但"我的一家"是主屏，用户每次进小程序都会触发，几百毫秒的服务端计算 + 全量 JSON 传输（几千个节点约 200—500KB）会让首屏明显迟滞。

缓存后：
- 布局计算只在数据变更后第一次请求时发生
- 客户端带上上次拿到的 `rev`，服务端比对一致就直接返回 `notModified`，**一个字节都不传**

对小程序的流量体验来说，这一层是必需的，不是优化。

### 3.13 `audit_log` / `notification`

审计日志：所有敏感动作（认领审批、合并节点、生成邀请码、批量导入）留痕。

通知：认领结果、提审结果、冲突提醒、有人认领了你附近的节点。**最后这条是拉活的关键**——"有人认领了你的堂弟，去看看对不对"，这种通知的打开率会很高。

---

### 3.14 `family_article` 谱文（2026-10-21）

编修历史、迁徙源流、谱序、凡例这类**长文章**，入口在首页家族卡下方。

为什么独立成表而不是塞进 `family` 表：一篇迁徙源流几千字、一篇谱序一修一篇，
同分类要能存多篇、能排序、能软删留痕——一行字段装不下，一对多就该是一张表。

| 字段 | 说明 |
|---|---|
| `category` | **固定枚举**：1 谱序 / 2 编修历史 / 3 迁徙源流 / 4 凡例 / 5 字辈派语 / 6 其他。同分类可多篇（历次修谱各一篇谱序） |
| `title` / `content` | 标题 128 字；正文 MEDIUMTEXT，**纯文本**、按空行分段（启明拍板 V1 不做富文本） |
| `sort_order` | 同分类内排序。列表按 `category, sort_order, id` 排——老谱目录的顺序 |
| `status` | 1 正常 / 0 软删。删除是软删：「家族撤回权」在审计上要有据可查 |
| `created_by` / `updated_by` | 留痕。写不走修订审核（文章不像世系字段容易引发纠纷），所以留痕靠这两列 |

**权限**：读 = 本族成员（`user_family` 有行）；写 = 房长及以上，
**按路径里的 familyId 查 `user_family.role`**——`app_user.role` 是"当前族"的
快照，文章接口的族在路径里，两者可能是不同的族。这条区别别的写接口没有。

## 四、脱敏规则（决策第 4 条的落地）

### 4.1 为什么放在 API 层而不是数据库视图

如果用数据库视图做脱敏，规则一变就要改视图、迁移数据。而脱敏规则**一定会变**——今天合规要求宽松，明天可能收紧；今天只对访客脱敏，明天可能要求对全体族人脱敏。

放在 API 层，改动就是几行代码。代价是：**任何一个新的查询接口都必须记得走脱敏函数**，漏一个就泄露。所以实现上强制约定：所有返回 person 数据的接口必须经过 `projectPerson(person, viewer, ctx)` 统一投影函数，不允许直接返回数据库行。

### 4.2 可见性矩阵

分界线是**有没有认领**，不是"是不是近亲"——2026-10-16 调整，理由见下。

| 字段 | 访客 / 未认领 | 已认领·旁系 | 已认领·近亲 | 族管理员 |
|---|---|---|---|---|
| 在世者姓名 | `陈*明` | 陈启明 | 陈启明 | 陈启明 |
| 在世者出生 | 仅年份 | 仅年份 | 年月日 | 年月日 |
| 在世者职业 | 隐藏 | 隐藏 | 显示 | 显示 |
| 在世者生平 | 隐藏 | 隐藏 | 显示 | 显示 |
| 已故者全部字段 | 显示 | 显示 | 显示 | 显示 |
| 在世者联系方式 | — | — | — | — |
| 详细住址 | — | — | — | — |

**为什么认领之后姓名就全给**：原来的判定是"近亲 = 直系上下 3 代 + 兄弟姐妹 + 配偶"，实测下来不对劲——认领之后打开全族总览，看到的是满屏 `陈*梁`、`陈*华`（伯父、堂侄那一支），而"全族总览"这一屏存在的意义就是看清整个族的结构，名字糊掉等于白做。

更关键的是逻辑上自相矛盾：身份确认已经改成**答题自证、不经任何审批**，理由是"同族的码只会分享给族人，阻塞的代价远大于冒领的代价"。既然认领的门槛都放到这个程度，认领之后还遮着同族人的名字就说不通了。

所以姓名一项绑到"认领"上，防线退回到它该在的位置——**未认领的访客**（族浏览码会被转发到族外，那一档必须继续打码）。

**只放开姓名。** 出生日期精度、职业、生平仍按近亲口径守着——那几项的个人信息浓度比姓名高，没必要跟着放大。

**近亲的定义**（仍然用于上面那几项，也用于"我的一家"的范围）：直系上下 3 代 + 兄弟姐妹 + 配偶。近亲集合由 `RelationGraph.close_relatives()` 算出。与"我的一家"视图范围保持一致——**用户在同一屏里看到的人，就该是他能看全的人**。

**已故者全部公开**，包括生卒、葬地、生平。这是史料，也是产品的核心价值。

`privacy_level=4`（私密）的行，**除了本人和管理员，谁都不返回**——包括近亲。给用户一个"这条我不想让人看"的出口。

### 4.3 不采集的字段（硬约束）

以下字段在 `person` 表中**不存在**，任何接口也不接受：

- 手机号
- 详细住址（`native_place` 仅到乡镇级，输入框加提示"请勿填写详细地址"）
- 身份证号
- 银行卡 / 财务信息

**判断标准很简单：这个字段对"记录家族血脉"这件事有没有用？** 手机号没用——三十年后它就是一条过期的垃圾数据，现在却是实打实的风险敞口。

## 五、不加物理外键的取舍

`schema.sql` 里所有关联字段只建索引，**不建 `FOREIGN KEY` 约束**。

**理由：**

1. **批量导入会被外键拖死。** 老谱 OCR 导入是几万条记录一次性写入，外键校验在每条 insert 时都要回表检查，实测会慢数倍。
2. **合并/拆分节点是高频操作。** "这两个是同一人，合并"、"这一支挂错了，整体挪到另一房"——这类操作在外键约束下要走复杂的先删后插流程，还容易被 `RESTRICT` 拦住。
3. **软删除用不上外键语义。** 我们靠 `status=0` 和 `merged_into_id` 表达删除与合并，不做物理删除，`CASCADE` 没有用武之地。

**代价（必须正视）：** 应用层写错就会产生脏数据——指向不存在的人的 `parent_child`、孤儿 union。

**对策：** 提供一个一致性巡检 SQL 脚本，定时跑，输出孤儿记录清单。巡检项至少包括：

- `parent_child.child_id` 指向不存在的 person
- `parent_child.union_id` 指向不存在的 union
- 没有 `is_primary=1` 的 parent_child 记录（说明这个人的主谱关系丢了）
- `person.family_id` 和其 parent_child 所属 family 不一致
- `family_union` 的双方属于不同 family（跨族婚姻的必要情况除外）
