**底部导航（2026-11-02 起）：族谱 / 动态 / 谱文 / 我的。**

| 位置 | 页面 | 为什么在这一格 |
|---|---|---|
| ① 族谱 | `pages/home` | 产品主屏：看谱、认人、补自己那一格 |
| ② 动态 | `pages/feed/feed` | 族里"最近谁在动"。**暂时是占位页**，内容口径未定，先把位置占住 |
| ③ 谱文 | `pages/articles/articles` | 编修历史、迁徙源流这类长文，族人最常翻；原先藏在首页家族卡里，现在提到一级入口 |
| ④ 我的 | `pages/mine/mine` | 身份、族书架、分享、理事会工作台，以及**待办**（原独立 tab，现并入首屏） |

**为什么把待办从 tab 撤下来**：一级入口要和"看谱 / 看动态 / 看谱文"同量级，而待办是"关于我自己的一个动作"，放进「我的」语义才对。它仍然在「我的」首屏（完整度 + 现在就能补的 3 条 + 逐条补完），没有降级成菜单深处。

**为什么谱文从家族卡搬到 tab**：谱文是"读"的内容，不该挂在"看树"的卡片里当附属；而且它跨族存在（每个族都有自己的谱文），放在底部比放在首页更稳。

**P0 五个页面就是 V1 的全部。** 这五个跑通，产品的核心闭环（看见自己 → 认领自己 → 补全自己 → 邀请家人）就成立了。P1/P2 是加法。

## 二、主流程：一个族人从点开链接到完成补全

这条路径是整个产品的生命线。**每一步的流失都要能被度量。**

```
【家族微信群】
   │  二叔转发的那条链接
   ▼
① 进入家族 · 落地页（未登录可看）
   │  ┌ 带码进来（家族群点链接 / 扫小程序码）→ 下面这屏
   │  └ 没带码（自己打开小程序）→ 输码屏：一个输入框 + 「为什么要一个码」
   │       查不到码就停在输码屏、当场换一个，不堵死
   │  · 上半：祠堂底图（自带空白黛青匾），堂号+族名是文字层叠在匾面上
   │    ——同一套底图所有族共用，换家族只换字（2026-10-28）
   │  · 下半（纸色区）：统计信息（定居地 · N 人 · N 世 · 始迁祖）
   │    + 邀请人 + 主按钮 [进去看看我家的谱] + [换一个家族码]
   │  · 未来理事会上传真实祠堂图（family.hallImage，待做）时
   │    退回「浮动牌匾卡」形态，底图与文字层解耦的设计不变
   ▼
② 需要登录才继续（点击主按钮时触发）
   │  · 一键微信登录，不索要手机号
   │  · 登录后自动 /invite/{code}/accept，拿到编辑范围
   ▼
③ 找到自己
   │  · 系统给出建议节点（"您可能是 陈国栋 的儿子"）
   │  · 也提供搜索框：搜父亲名 / 搜自己名
   │  · 点节点 → 底卡弹出 → [这就是我]
   ▼
④ 提交认领
   │  · 一句佐证："我父亲是陈国栋，我生于1988年"
   │  · 提交后提示：已提交，等待房长审核
   ▼
⑤ 审核期间可以先逛（关键：不要让用户等）
   │  · 能看全族树（脱敏）
   │  · 能看到自己的待补全清单（但提交按钮灰置，提示"审核通过后即可提交"）
   │  · 可以先把要填的内容写好存草稿 ← 降低等待的挫败感
   ▼
⑥ 审核通过 → 推送通知 → 回到待补全清单
   │  · "还差 3 个人：您父亲、您母亲、您配偶"
   │  · 填一个划掉一个
   ▼
⑦ 填完 → 生成邀请链接 → 转发到家族群 / 私下发给二叔
   │  · "二叔，爷爷那一支还差 4 个人，您帮我补一下"
   ▼
⑧ 二叔走同样的路径…… 回到 ①
```

**这个环能转起来，项目就成了。** 所以设计上的所有取舍都服务于一件事：**让第 ⑥ 步和第 ⑦ 步尽可能顺滑。**

## 三、我的一家（首页）—— 最需要打磨的一屏

### 3.1 布局与手势

| 交互 | 行为 | 约束 |
|---|---|---|
| 初始状态 | **自适应缩放填满屏幕**，锚点居中偏下 | 保证首屏能看见"我"和上下各一代 |
| 单指拖动 | 平移画布 | 边界回弹 |
| 双指捏合 | 缩放 | 限制 0.5x — 2.0x |
| 双击空白 | 在"适应屏幕"和"1.0x"之间切换 | — |
| 双击节点 | 以该节点为锚点，重绘"我的一家" | 有过渡动画 |
| 长按节点 | 快捷菜单：认领 / 编辑 / 邀请 / 定位到我 | — |

**初始缩放必须自适应，不能让用户自己去缩放找自己。** 打开就是"我"在屏幕中央，周围的家人围着他——这个第一印象决定了用户会不会继续往下点。

### 3.2 点击节点：底部半屏卡，而不是跳页

**这是一个重要的交互判断。**

如果点节点直接跳转到人物详情页，用户看完想回树上继续看别人，要退出、等页面恢复、重新定位——**空间位置感丢失了**。在家族树里"谁在谁的旁边"本身就是信息，跳页会把这个信息抹掉。

所以用半屏卡：

```
┌─────────────────────────────┐
│  ──                         │  ← 拖拽手柄
│  陈国栋                      │
│  第十九世 · 长房             │
│  1965年3月12日 · 教师        │
│  ─────────────────────      │
│  父：陈文山    母：王秀英     │
│  妻：李*芳                   │
│  子：陈启明 · 陈启华          │
│  ─────────────────────      │
│  [ 查看完整资料 ]  [ 这是我的 ]│  ← 全页入口放这里
└─────────────────────────────┘
```

卡片高度约 45%，向上拖可以展开成全屏（就是人物详情页）。

**半屏卡里就能看到关键关系，80% 的浏览需求在这里就满足了**；想深看的才走"查看完整资料"。这样用户能以很低的成本在树上游走。

### 3.3 路径高亮

从始祖到锚点的路径**永远加粗、用主色**，其他节点降到 40% 透明度。

```
始祖 ··············●═══════════●═══════●═══════◉═══════◉
                   │           │       │       │       │
              （灰）│      （灰）│  （灰）│  （加粗）│  （加粗·我）
```

这条线解决用户面对家谱的第一个问题：**"我在哪？"**

没有这条线，3000 人的树对用户来说就是一张无法进入的地图。有了这条线，"我从哪儿来"这个抽象概念变成了一条能看见的路径。

### 3.4 节点视觉规范

| 角色 | 样式 | 说明 |
|---|---|---|
| 本族男丁 | 实心卡片，墨色边框 | 主链 |
| 本族女儿 | 实心卡片，细边框，姓氏用主色 | 与男丁区分但同级 |
| 媳妇 | 浅底卡片，左侧短竖线 | 视觉上是配偶而非世系 |
| 女婿 / 外孙 | **虚线边框，浅灰** | 明确表达"外姓" |
| 已故 | 姓名后加淡色 "†" | 不用黑白照片等沉重处理 |
| 锚点"我" | 主色描边 + 微投影 + 呼吸动画 | 唯一有动效的节点 |

**外姓用虚线框的意义：** 决策第 2 条说外孙只在我的一家显示。虚线框在视觉上就传达"这是关联的人，不是本族世系"——**用户不需要读任何说明就能理解规则**，也不会有"为什么外孙不在全族树里"的困惑。

### 3.5 待补全角标

有缺失信息的节点右上角挂一个小圆点角标，数字是缺几项。

首屏顶部还有一条进度条：

```
咱们家的谱 · 完整度 62%
还差 87 位奶奶的名字  →  [去看看]
```

**这条进度条是整个产品最重要的运营位。** 它把"填补家族历史"这件抽象的事，变成一个可以看见进度的集体任务。87 这个数字比任何文案都有号召力。

## 四、待补全清单（`pages/fill`）—— 接力修谱的引擎

### 4.1 页面结构

```
┌─────────────────────────────────┐
│  还差 3 个人                     │
│  ▓▓▓▓▓▓▓▓░░░░░  2/5 已完成       │
├─────────────────────────────────┤
│  ① 您父亲叫什么名字？             │
│     家谱中尚未记录您的父亲        │
│     [ 填写 ]                     │
├─────────────────────────────────┤
│  ② 您母亲的名字是？               │
│     家谱中记载为「配李氏」        │
│     [ 补上名字 ]                 │
├─────────────────────────────────┤
│  ③ 您的配偶叫什么名字？           │
│     [ 填写 ]                     │
└─────────────────────────────────┘
```

### 4.2 一次只问一个

点开第 ② 项：

```
┌─────────────────────────────────┐
│  ← 返回                          │
│                                  │
│  您母亲的名字是？                 │
│                                  │
│  ┌─────────────────────────┐    │
│  │  李秀英                  │    │
│  └─────────────────────────┘    │
│                                  │
│  老谱上只记了姓：                 │
│     修改前   配李氏              │
│     修改后   配李秀英            │  ← 实时对比
│                                  │
│  [ 提交 ]  [ 暂不填写 ]           │
└─────────────────────────────────┘
```

**"修改前 / 修改后"的实时对比，是产品最强的情绪点。** 用户填下母亲名字的那一刻，看到"配李氏"变成"配李秀英"，这不是数据录入，这是**把一个被历史省略掉的人重新写回来**。这个瞬间值得做成产品里最有仪式感的一屏。

### 4.3 三种任务类型

| 类型 | 场景 | 交互 |
|---|---|---|
| `create_person` | 父亲、配偶等尚未记录的人 | 极简表单，只问姓名（其他都可选） |
| `update_field` | 补全"配某氏"的姓名、缺的生日 | 单字段 + 前后对比 |
| `create_union` | 记录一段婚姻 | 姓名 + 婚期（可选） |

**`create_person` 只强制问姓名。** 一次问 20 个字段的表单是转化率杀手；问一个名字，用户 10 秒能填完；填完之后如果用户愿意，再问生日、职业——**"再补一点"永远比"请一次填完"有效**。

### 4.4 清单怎么生成

服务端 `GET /person/{id}/missing` 按以下规则算：

| 检查项 | 触发条件 |
|---|---|
| 父亲缺失 | 该人无 `is_primary=1` 的父系 union |
| 母亲姓名缺失 | 父系 union 的 `partner_b` 为 NULL，或 partner_b 的 `name` 为 NULL |
| 配偶缺失 | 在世成年但无任何 union |
| 子女缺失 | 有 union 但无 `parent_child` |
| 外孙缺失 | **可选任务**，仅在用户主动开启"记录女儿的家庭"时出现（决策第 2 条：外孙是否入谱由用户决定） |
| 生卒缺失 | 已故但无 `death_date` |
| 葬地缺失 | 已故但无 `burial_place` |

**"为什么问这个"必须在界面上说清楚**（`reason` 字段）。用户不反感被问，反感的是莫名其妙被问。

## 五、邀请流程（决策第 5 条，方案 C 的界面落地）

### 5.1 邀请管理页

```
┌─────────────────────────────────┐
│  邀请家人一起补                │
├─────────────────────────────────┤
│  【发给全族的】                  │
│  全族浏览码  AB12CD34            │
│  只能看，不能改                   │
│  [ 复制 ] [ 转发到群 ]           │
├─────────────────────────────────┤
│  【发给亲人的】                  │
│  我的编辑码  K7M2P9QT            │
│  可以填写：您本人及父母、子女     │
│  （共 11 个节点）                │
│  [ 复制 ] [ 转发给二叔 ]         │
│  已使用：1 次 ｜ 有效期至 10-24   │
├─────────────────────────────────┤
│  我发出的邀请                    │
│  · 二叔（陈*海）已加入           │
│  · 大姐（陈*华）未使用           │
└─────────────────────────────────┘
```

**两种码在同一个页面，用视觉分组区分，并写清"只能看"和"可以填"的差别。** 用户不需要理解权限模型，他只需要知道哪个发给谁。

### 5.2 分享文案由服务端生成

```json
{ "shareText": "二叔，我在做咱们家的电子家谱，您点这里把爷爷那支的信息补一下" }
```

**为什么不让用户自己想：** 大部分用户面对分享框会卡住，最后一咬牙发了句"看看这个"，转化率极低。给一句现成的、带称呼和具体动作的话术，转发率会显著不同。这属于"产品替用户把最难的那一步做了"。

### 5.3 编辑码的范围呈现

生成前让用户确认范围：

```
这个链接可以填写这些人的信息：

     陈*山（祖父）
        ├ 陈*栋（父）★
        │   ├ 陈启明（本人）★
        │   └ 陈启华 ★
        └ 陈*梁（叔）

共 11 个节点，其中 ★ 是你的直系

[ 生成链接 ]
```

**把权限范围可视化，用户才有安全感**——他知道自己发出的链接不会让人改到别人家。这直接解决了"万一被乱改怎么办"的顾虑，而这个顾虑是家族群里长辈最大的抵触来源。

## 六、认领流程

```
① 在树上找到自己（搜索 / 建议 / 从父亲页面找）
   ▼
② 点节点 → 底卡 [这就是我]
   ▼
③ 认领确认页
   ┌───────────────────────────┐
   │  您认领的是：              │
   │  陈启明 · 第二十世 · 长房   │
   │  父：陈国栋  母：李*芳      │
   │                            │
   │  请补充一句佐证（选填）：    │
   │  ┌──────────────────────┐ │
   │  │ 我父亲是陈国栋，我生于  │ │
   │  │ 1988年                │ │
   │  └──────────────────────┘ │
   │                            │
   │  审核人：陈国梁（长房房长） │
   │  [ 提交认领 ]              │
   └───────────────────────────┘
   ▼
④ 提交后
   · 页面上该节点出现"待审核"角标
   · 用户可以继续浏览，可以填草稿
   · 首页顶部出现状态条："您的认领正在审核中"
   ▼
⑤ 审核结果通知
   · 通过 → 引导进入待补全清单（转化关键点）
   · 驳回 → 说明原因 + [ 我可以申诉 ]
   ▼
⑥ 冲突（40901）
   · "这个节点已被 陈启华 认领"
   · 两个出口：[ 我是本人，提交申诉 ] [ 我不是，去找我的节点 ]
```

**第 ③ 步的"审核人是谁"要露出。** 显示一个具体的名字（"长房房长 陈国梁"）而不是"管理员"，信任感和提交率会明显不同——**用户面对一个人时更愿意提交，面对一个系统时会犹豫。**

## 七、审核台（房长视角，`pages/review`）

### 7.1 差异对比是第一屏

房长要审的东西必须**一眼能判断**，不能让他去翻资料。

```
┌──────────────────────────────────┐
│  待审 12 条                       │
├──────────────────────────────────┤
│  陈启明（之子）提交                │
│  修改 陈国栋（父）                 │
│                                   │
│  出生日期   1965年    →  1965年3月12日  │
│  职业       —         →  教师          │
│                                   │
│  [ 通过 ]  [ 驳回 ]  [ 暂缓 ]      │
├──────────────────────────────────┤
│  陈启华（本人）提交                │
│  新增 子女 陈小雨                 │
│  ...                              │
└──────────────────────────────────┘
```

关键设计：
- **`submitterRelation`（之子 / 本人 / 之侄）必须显示** —— 房长看到一个"之子"提交的修改，基本可以直接通过
- **一次审核一条，但支持批量勾选通过** —— 首期导入期会有几百条待审，单条点会崩溃
- **绝不提供"全部通过"** —— 家谱数据一旦批量放行，错误会扩散到全族

### 7.2 冲突处理页

```
陈国栋的出生日期，有两条不一致的填报：

  ◉ 1965年3月12日   陈启明（子）  09-20 提交
  ○ 1965年       陈国华（侄）  09-21 提交

  [ 采信陈启明 ]
  [ 驳回双方，让他们先确认 ]

  备注（必填）：________________
```

**备注必填，且页面上有一行固定的说明：**

> 家谱中的记载会传给后代。若双方说法不一致，建议先与家中长辈电话确认，再在此处记录采信理由。

平台不做辈分裁判。我们是工具，不是祠堂。

## 八、全族总览（我的支系已退休）

### 8.1 ~~我的支系（虚拟列表）~~ —— 2026-10-21 退休

原设计是按世次分行、横向滚动的世系表。**已废弃**，理由：

- 它想解决的是"一次看全一支"，但真实规模（十几代 / 200 活人）下这张表读不出结构，且它的口径（含媳妇）与总览（只含丁口）打架
- 用户真正的需求是"我关心我自己"，不是"看完整个支系"
- 替代路径已经够用：**换锚点逐代上下移动**（点最上面那位 → 他成为中心），要整体形状就去下面的全族总览

代码里的 `view=lineage` 只为兼容保留，端上没有任何入口。

### 8.2 全族大宏图（Canvas 谱牌树，2026-10-29 定稿）

**形态：一张真正的关系图**。节点是 64×72 的谱牌（纸白圆角卡 + 顶部世色条 + 居中姓名 + 在世黛青 / 已故灰纸），父子用正交折线连到下一代，配偶用金色横线连在一起。

- **1:1 固定缩放，不缩放**。卡 64×72 屏幕像素、名字 11px（2026-11-02 从 88×96/22px 缩半），无论多少人都是可读的
- **上下左右滑动**看全族：单指拖动；不提供"缩到全貌"——564 人整屏适配时字号 0.47px，等于一片糊点
- **左侧一列「世代丁口」固定**：屏幕坐标绘制，横向滑不跑、纵向对齐各代那一行（第几世、多少人）；点人命中时排除这一栏
- 落点：未指定时落在始祖（世代最小 + 横坐标最小），从始祖往里看
- **点谱牌 = 浮出操作环**（上父母 / 下子女 / 左配偶 / 右详，与「我的一家」的加家人同一套交互）；环上的「详」直接进个人页——不开半屏详情卡，树铺满全屏会把半屏卡压住（2026-11-02 实报）
- 人物详情页的「看他在树上的位置」跳到这里，目标居中 + 烫金外圈（`?view=overview&focus=<id>`，focus 不带权限）
- 只画视口内的节点与线段（564 节点全画会掉帧；裁剪后可见的通常只有二三十个）

**为什么是 Canvas 而不是 view 拼卡：** 15 代 / 500+ 人用绝对定位要 2000+ 个节点、画布宽到 9500px，view 拼不出这个量级。Canvas 只负责画，布局仍由服务端算（Reingold-Tilford），端上不排。

**为什么从"色块骨架"改成"带姓名的谱牌"：** 点线骨架只画结构不画姓名，用户看到的是"一片认不出的点"（2026-10-29 实报"只有一个色块占位"）。名字是这一屏的第一信息，关系是第二信息——两者都得有，才叫"大宏图"。

## 九、性能与工程约束

| 项 | 要求 | 理由 |
|---|---|---|
| 首屏（我的一家） | < 1.5s 可见 | 主屏，慢一次就流失一批 |
| 树接口 | 缓存命中 < 100ms，未命中 < 500ms | 布局算法在服务端，端上不算 |
| 树 JSON | `mine` < 30KB，`overview` lite < 50KB | 小程序流量敏感 |
| 布局缓存 | 必须有，靠 `data_rev` 失效 | 见数据库设计 3.11 |
| 分包 | 核心四页在主包，其余分包 | 主包体积限制 |
| 节点上限 | WXML 视图 ≤ 300 节点 | 超过改用虚拟列表 |
| 图片 | 人物头像非必需，不做 | 老谱里的人没有照片，强做会变成"没头像的空框" |

### 关于头像的判断

**V1 不做人物头像。** 老谱里的人没有照片，做头像位会导致整棵树布满灰色占位圆，视觉上非常失败。用**姓名 + 世次**做节点内容就够了——这也是传统家谱的呈现方式，本来就该长这样。

在世者可以自愿上传，但默认不显示在树上，只出现在人物详情页。

## 十、V1 验收标准

产品跑通的判断标准不是"功能都做完了"，而是这几个数字：

| 指标 | 目标 | 说明 |
|---|---|---|
| 认领率 | ≥ 6% | 3000 人的族，认领 180 人 |
| 待补全完成率 | ≥ 40% | 认领用户中，完成清单的人数占比 |
| 邀请转化 | 每次邀请 ≥ 1.2 人 | 一个用户平均带来一个以上的人 |
| 单族覆盖 | 一个完整房（≥300 人） | 不是全族，是一个房跑通 |
| 错误率 | 审核驳回率 < 15% | 高于 15% 说明引导有问题 |

**这套指标里最关键的洞察是：V1 不追求覆盖整个宗族，只追求把一个房跑通。** 房是家谱里天然的责任单元——同一个房的人有共同的祖父母、彼此认识、在同一个微信群里。让一个房先完整地动起来，比在全族里拉 300 个孤立的人有用得多。
